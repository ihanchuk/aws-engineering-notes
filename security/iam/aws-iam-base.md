# Руководство по AWS IAM: От Экшенов до Ролей за 4 шага

Понимание безопасности в AWS часто вызывает сложности. На самом деле всю иерархию AWS IAM (Identity and Access Management) можно разложить на четыре понятных уровня: от атомарного действия до сложных конфигураций ролей.

---

### Уровень 1. Экшен (Action) — Базовый уровень
В самом низу нашей иерархии находится **Action (Действие)**. Это атомарное разрешение на выполнение конкретной операции с определенным объектом или сервисом AWS. Экшен — это минимальный кирпичик безопасности, который существует в природе AWS.

* **Примеры:** 
  * `s3:GetObject` — право скачать файл из бакета.
  * `rds-db:connect` — право подключиться к базе данных.
  * `ec2:StartInstances` — право запустить виртуальный сервер.

---

### Уровень 2. Политика (Policy) — Набор экшенов
Чуть выше находится **Policy (Политика)**. Это текстовый JSON-документ, который представляет собой упорядоченный набор экшенов. Политики разделяются на два фундаментальных типа в зависимости от того, к чему они прикрепляются:

#### 1. Resource-Based Policies (Политики на основе ресурсов)
Этот тип политик описывает, **что и кому** разрешено делать с конкретным ресурсом. Они прикрепляются напрямую к объекту (например, к бакету S3). 

Такие политики **обязательно требуют наличия элемента `Principal`** — сущности, которой мы делегируем права. Принципалом может выступать кто угодно: другой сервис AWS, конкретный пользователь или сторонний AWS-аккаунт.

* **Пример JSON (Resource-Based policy для S3-бакета):**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowExternalAccountToPutObjects",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:root"
      },
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::my-company-shared-bucket/*"
    }
  ]
}
```

#### 2. Identity-Based Policies (Политики на основе удостоверений)
Этот тип политик прикрепляется к сущностям (IAM-пользователям, группам или ролям). Они описывают, **что конкретно эта сущность имеет право делать** с другими сервисами AWS. 

Элемент `Principal` здесь **отсутствует**, так как права автоматически прописываются для того объекта, на который эта политика прикреплена.

* **Пример JSON (Identity-Based policy для чтения из S3):**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowReadAccessToS3",
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket",
        "s3:GetObject"
      ],
      "Resource": [
        "arn:aws:s3:::my-company-shared-bucket",
        "arn:aws:s3:::my-company-shared-bucket/*"
      ]
    }
  ]
}
```

### Уровень 3. Роль (Role) — Сводный набор полномочий
**IAM-роль (Role)** — это автономный набор полномочий, который формируется строго на основе комбинации двух обязательных политик. У роли нет постоянных паролей или секретных ключей. Ее структура жестко определена следующими компонентами:

1. **Trust Policy (Политика доверия):** Описывает, **КОМУ** мы доверяем использовать эту роль.
2. **Permission Policy (Политика разрешений):** Описывает, **ЧТО** именно разрешено делать (это обычная Identity-Based политика, то есть набор экшенов).

Сама **Trust Policy** всегда состоит из двух обязательных элементов:
1. `Principal` (целевой ARN пользователя, AWS-сервиса вроде `://amazonaws.com` и т.д.).
2. Разрешение на вызов службы токенов безопасности — экшен `sts:AssumeRole`.

* **Пример JSON (Полная анатомия роли для AWS Lambda):**

**Часть А: Trust Policy (Доверяем сервису Lambda временно брать эту роль)**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "://amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**Часть Б: Permission Policy (Разрешаем Лямбде в этой роли писать логи в CloudWatch)**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "arn:aws:logs:*:*:*"
    }
  ]
}
```

### Важные понятия: Что такое ARN и Principal?

Для составления политик безопасности необходимо четко понимать два термина, на которых держится вся адресация и авторизация в AWS:

#### 1. ARN (Amazon Resource Name)
**ARN** — это уникальный глобальный идентификатор любого ресурса в облаке AWS. Абсолютно все объекты (S3-бакет, IAM-пользователь, VPC, EC2-инстанс или Lambda-функция) имеют свой собственный неизменяемый ARN. Он имеет строгую структуру, разделенную двоеточиями:

`arn:aws:сервис:регион:id-аккаунта:тип-ресурса/имя-ресурса`

* *Пример для S3 бакета:* `arn:aws:s3:::my-company-shared-bucket` (У S3 нет региона и ID аккаунта в ARN, так как имена бакетов глобально уникальны).
* *Пример для IAM роли:* `arn:aws:iam::123456789012:role/my-lambda-execution-role`

В блоке политики `Resource` вы всегда указываете именно ARN того объекта, над которым выполняется экшен.

#### 2. Principal (Принципал)
**Principal** — это ответ на вопрос **«КТО запрашивает доступ?»**. Это объект в блоке JSON-политики, которому вы явно разрешаете или запрещаете выполнять действия. 

Принципалом может быть:
* AWS-сервис (`"Service": "://amazonaws.com"`).
* Корневой аккаунт AWS или конкретный IAM-пользователь (`"AWS": "arn:aws:iam::123456789012:user/developer-ivan"`).
* Любой авторизованный пользователь (используя дикую карту `*`).

Элемент `Principal` используется исключительно в **Resource-Based** политиках и в **Trust Policy** для IAM-ролей. В Identity-Based политиках он не нужен, так как принципалом автоматически становится тот, к кому эта политика прикреплена.

### Уровень 4. Динамика работы через AWS STS
Когда ваша Lambda-функция или любой другой сервис запускается, встроенная служба **AWS STS (Security Token Service)** сверяется с *Trust Policy* роли. Убедившись, что вызывающая сущность совпадает с указанным `Principal` и имеет право на `sts:AssumeRole`, STS генерирует краткосрочные временные ключи доступа. С этого момента запущенный код действует строго в рамках прав, очерченных в прикрепленной *Permission Policy*.
