# Настройка рантайм-роли Lambda для переключения (Assume Role) в другой аккаунт

Вы можете настроить Lambda-функцию в одном аккаунте (Аккаунт А) для доступа к ресурсам в другом аккаунте (Аккаунт Б). Для этого в Аккаунте Б создается специальная роль IAM. Эта роль делегирует права Lambda-функции из Аккаунта А на использование сервисов и ресурсов внутри Аккаунта Б.

---

## Примеры JSON-политик

Чтобы реализовать эту схему, вам понадобятся две политики безопасности.

### 1. Инлайн-политика (Inline Policy) для Аккаунта А
Эта политика прикрепляется к родной роли выполнения Lambda-функции в **Аккаунте А**. Она разрешает функции временно «примерить» на себя роль из чужого аккаунта с помощью сервиса AWS STS.

```json
{
  "Version": "2012-10-17",
  "Statement": {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::222222222222:role/role-on-source-account"
  }
}
```
* **Важное примечание:** Замените `222222222222` на реальный ID Аккаунта Б (целевого), а `role-on-source-account` — на имя роли, созданной в Аккаунте Б.

### 2. Политика доверия (Trust Policy) для Аккаунта Б
Эта политика настраивается внутри самой роли в **Аккаунте Б**. Она указывает, какому именно внешнему объекту разрешено переключаться на эту роль (кому мы доверяем).

```json
{
  "Version": "2012-10-17",
  "Statement": [
      {
          "Effect": "Allow",
          "Principal": {
              "AWS": "arn:aws:iam::111111111111:role/my-lambda-execution-role"
          },
          "Action": "sts:AssumeRole"
      }
  ]
}
```
* **Важное примечание:** Замените `111111111111` на ID Аккаунта А (где находится Lambda), а `my-lambda-execution-role` — на точное имя роли выполнения вашей Lambda-функции.
