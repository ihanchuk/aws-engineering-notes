# Методы исправления таймаутов в AWS Lambda

Чтобы устранить проблему с таймаутами, последовательно примените следующие технические решения в зависимости от выявленной причины.

---

## 1. Исправление сетевых настроек внутри VPC

Если ваша Lambda подключена к VPC и должна делать запросы в интернет (например, к внешним API), стандартная конфигурация заблокирует трафик. 

**Как настроить сеть правильно:**
* **Размещение в приватных подсетях:** Перенесите Lambda-функцию из публичных подсетей в приватные (Private Subnets). Lambda никогда не должна находиться в публичной подсети напрямую.
* **Настройка NAT Gateway:** В публичной подсети той же VPC создайте **NAT Gateway** (или NAT Instance) и присвойте ему Elastic IP.
* **Таблицы маршрутизации (Route Tables):** В таблице маршрутизации приватной подсети (где сидит Lambda) добавьте маршрут `0.0.0.0/0`, указывающий на созданный NAT Gateway. Теперь трафик пойдет наружу.
* **VPC Endpoints (Альтернатива для сервисов AWS):** Если Lambda внутри VPC общается только с другими сервисами AWS (например, S3 или DynamoDB), не обязательно настраивать дорогой NAT Gateway. Создайте бесплатные **VPC Gateway Endpoints** для S3/DynamoDB прямо внутри вашей сети.

---

## 2. Корректировка лимитов и ресурсов в конфигурации Lambda

Часто функция падает просто потому, что ей не хватает времени или вычислительной мощности для выполнения тяжелой задачи.

* **Увеличение таймаута функции:** Зайдите в настройки функции (*Configuration -> General configuration*) и увеличьте параметр **Timeout**. По умолчанию AWS ставит всего 3 секунды. Оцените реальное время работы вашей задачи и поставьте лимит с запасом (например, 30 секунд или 1-2 минуты). Максимальный лимит — 15 минут.
* **Выделение дополнительной памяти (Memory):** В тех же общих настройках увеличении объема памяти (например, с 128 МБ до 1024 МБ или выше). **Важно:** AWS выделяет мощность процессора (CPU) пропорционально объему памяти. Больше памяти — мощнее процессор. Код отработает быстрее, и таймаут исчезнет.

---

## 3. Оптимизация кода и настройка таймаутов на уровне приложения

Защитите свою функцию от бесконечного ожидания "зависших" внешних серверов.

* **Настройка HTTP/Socket таймаутов в коде:** Никогда не используйте стандартные HTTP-клиенты без явного указания таймаутов. Если вы вызываете сторонний API через `Axios`, `Fetch` или `boto3`, всегда задавайте жесткий лимит ожидания (например, `timeout: 5000` мс).
* **Следование правилу «Меньше, чем таймаут Lambda»:** Время ожидания вашего HTTP-клиента в коде должно быть **меньше**, чем общий таймаут самой функции Lambda. Если лимит Lambda — 10 секунд, настройте HTTP-клиент на 7 секунд. Тогда при зависании стороннего API ваш код сам прервет операцию, перехватит ошибку в блок `try-catch` и запишет в CloudWatch понятный лог, вместо того чтобы позволить AWS аварийно убить функцию.
* **Оптимизация тяжелых блоков:** Выносите инициализацию тяжелых объектов (подключения к базам данных, создание клиентов AWS SDK) **за пределы** основного обработчика `handler` (в глобальную область видимости файла). Это позволит переиспользовать соединения при повторных вызовах функции и сократит время работы.
