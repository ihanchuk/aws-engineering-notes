# Amazon SQS in details

При проектировании систем на базе Amazon SQS (Simple Queue Service) разработчики часто сталкиваются со специфическим поведением распределенной архитектуры AWS. Ниже собраны ключевые особенности, о которых нужно знать заранее.

---

### 1. Видимость сообщений и таймаут (Visibility Timeout)

Когда потребитель (*consumer*) забирает сообщение из очереди, оно **не удаляется** автоматически, а временно скрывается от других потребителей на период `Visibility Timeout`.

* **Проблема «зомби-сообщений»:** Если воркер не успевает обработать сообщение за отведенное время (например, завис внешний API или тяжело отрабатывает запрос в БД), сообщение снова становится видимым в очереди. Его считывает другой воркер. В результате одно и то же сообщение начинает обрабатываться **параллельно в двух местах**.
* **Решение:** Если обработка затягивается, динамически продлевайте таймаут видимости через API-вызов `ChangeMessageVisibility`.

### 2. Ловушки очередей FIFO (First-In-First-Out)

Хотя FIFO-очереди гарантируют строгий порядок и доставку «строго один раз», их логика имеет два важных ограничения:

* **Блокировка группы (`MessageGroupId`):** Порядок сообщений гарантируется только *внутри* одной группы. Если обработка одного сообщения из группы `Group_A` завершилась ошибкой или зависла, **вся группа `Group_A` блокируется** — следующие за ним сообщения будут ждать. При этом сообщения из `Group_B` продолжат обрабатываться параллельно.
* **Окно дедупликации (`MessageDeduplicationId`):** SQS автоматически отслеживает и удаляет дубликаты сообщений (по хэшу контента или переданному ID) только в течение **5 минут**. Если отправить точно такое же сообщение через 5 минут и 1 секунду, SQS пропустит его как новое.

### 3. Задержка при очистке очереди (Purge)

Команда `PurgeQueue` позволяет мгновенно удалить все сообщения из очереди, но у этого действия есть временной лаг.

* **Нюанс:** Процесс очистки может занимать до 60 секунд. Если вы вызовете `Purge`, а затем сразу (в течение этой минуты) отправите в очередь новые валидные сообщения, они с высокой вероятностью **тоже будут удалены** в процессе очистки.

### 4. Мертвые буквы (DLQ) и бесконечные циклы

Очередь мертвых букв (*Dead Letter Queue*) необходима для изоляции поврежденных сообщений (*poison pills*), которые система не может обработать.

* **Настройка `maxReceiveCount`:** Этот параметр определяет, сколько раз воркер попытается обработать сообщение перед его сбросом в DLQ. Значение не должно быть равно `1`. В противном случае любой мимолетный сетевой сбой или плановый перезапуск контейнера с воркером навсегда отправит корректное сообщение в DLQ без единой попытки повторной обработки.
* **Обратный эффект:** Если DLQ вообще не настроена, бракованное сообщение будет бесконечно возвращаться в очередь, перегружать CPU воркеров и генерировать лишние платные запросы к AWS.

### 5. Архитектура распределения и типы опроса

SQS — сильно распределенная система. Сообщения физически хранятся на множестве разных серверов AWS.

* **Короткий опрос (Short Polling):** Используется по умолчанию. При запросе SQS опрашивает лишь *часть* своих серверов. Из-за этого метод `ReceiveMessage` может вернуть пустой ответ (0 сообщений), даже если в очереди прямо сейчас есть данные.
* **Решение:** Всегда настраивайте **Long Polling** (параметр `WaitTimeSeconds` > 0, максимум 20). Это заставляет SQS опрашивать все сервера и ожидать появления сообщений. Такой подход также снижает расходы, так как уменьшает количество пустых запросов.

### 6. Специфика удаления сообщений

Распространенная ошибка новичков — попытка удалить сообщение с помощью `DeleteMessage`, передавая туда `MessageId`.

* **Как правильно:** Сообщение можно удалить **только** по идентификатору `ReceiptHandle`. Этот хэндл уникален для *каждого конкретного факта чтения* сообщения. Если сообщение превысило таймаут видимости, вернулось в очередь и было прочитано другим воркером, ваш старый `ReceiptHandle` станет невалидным, и удалить сообщение по нему уже не получится.
