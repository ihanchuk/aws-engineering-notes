# Различия между Service Task и Activity Task в AWS Step Functions

В архитектуре **AWS Step Functions** фундаментальная разница между **Activity Task** и **Service Task** (интеграцией с сервисами AWS) заключается в том, **где и как исполняется код** задачи.

## Короткий ответ

- **Service Task (Режим сервисов):** Шаг выполняется полностью **внутри инфраструктуры AWS** (например, запуск Lambda-функции, ECS-таски или запрос к DynamoDB). Step Functions сама управляет вызовом и ждет ответа.
- **Activity Task (Режим активностей):** Шаг передает управление **вашему внешнему воркеру** (программе на EC2, онпремиз-сервере или локальном компьютере). Этот воркер сам должен периодически опрашивать Step Functions, забирать задачу, выполнять её и возвращать результат.

---

## Подробное сравнение

| Критерий                    | Service Task (Интеграция с сервисами)                                             | Activity Task (Активности)                                                                                    |
| :-------------------------- | :-------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------ |
| **Где выполняется код**     | В управляемых сервисах AWS (Lambda, ECS, Batch, SNS, DynamoDB и др.).             | На любых ваших мощностях (EC2, контейнеры, локальные сервера, ПК).                                            |
| **Принцип работы**          | **Push-модель:** Step Functions сама вызывает API целевого AWS-сервиса.           | **Pull-модель:** Ваш внешний воркер постоянно опрашивает API (`GetActivityTask`) в ожидании работы.           |
| **Таймауты и длительность** | Ограничено лимитами конкретного сервиса (например, для Lambda максимум 15 минут). | Может длиться **до 1 года** (максимальная длительность выполнения стейт-машины).                              |
| **Сетевой доступ**          | Нужен доступ из AWS к целевому сервису (обычно внутри облака AWS).                | Воркеру нужен только **исходящий** доступ в интернет/AWS API. AWS не нужно «достукиваться» до вашего сервера. |
| **Сложность настройки**     | **Низкая.** Всё настраивается прямо в JSON/ASL-коде стейт-машины через IAM-роли.  | **Средняя.** Нужно писать код для воркера, который будет крутиться в бесконечном цикле и запрашивать задачи.  |

---

## Когда что выбирать?

### Выбирайте Service Task, если:

- Вы строите классическое **cloud-native** (бессерверное) приложение.
- Код задачи можно упаковать в AWS Lambda или запустить как короткую задачу в AWS ECS/Fargate.
- Вам нужно просто передать данные из одного сервиса AWS в другой (например, положить файл в S3 и отправить уведомление в SNS).

### Выбирайте Activity Task, если:

- **Инфраструктура находится вне AWS:** Например, вам нужно запустить скрипт на локальном сервере в вашем собственном дата-центре (on-premises).
- **Задачи длятся очень долго:** Процесс занимает несколько часов или дней, что превышает лимиты AWS Lambda.
- **Уникальные требования к железу:** Программе нужен доступ к специфическому оборудованию, проприетарному софту или огромному объему RAM/GPU, который сложно или дорого развернуть в ECS.
- **Воркер заблокирован файрволом:** Так как воркер сам ходит в AWS за задачами (Pull), вам не нужно открывать входящие порты на вашем сервере.
